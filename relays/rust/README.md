# Rust relays

Rust has **no auto-instrumentation for any tool**, so — same precedent as
`relays/go` — the relays use each vendor's documented propagator API with
documented carrier types and explicit `opentelemetry::Context` plumbing:
extract on inbound, start a span parented on the extracted context, pass that
context to the outbound leg, inject from it there. No relay code ever
composes, copies, or hand-builds a propagation header; every header name and
value is produced by the tool's propagator. Datadog's own Rust docs prescribe
exactly this manual extract/inject pattern, because "there is no automatic
instrumentation for Rust"
([Trace Context Propagation → Rust](https://docs.datadoghq.com/tracing/trace_collection/trace_context_propagation/?tab=rust)).

One crate per tool — `otel/`, `datadog/`, `none/`, each a `Cargo.toml` with
its own committed `Cargo.lock` — over one shared source tree (the layout
relays/ruby uses with `gemfiles/<tool>` and relays/node with `tools/<tool>`):

- `src/lib.rs`, `src/inbound.rs`, `src/forward.rs` — transports, env, /info;
  `src/propagation.rs` — the carriers; `build.rs` — gRPC stubs and the
  `/info` version stamps. Compiled into every tool's crate.
- `otel/` builds `src/bin/relay-otel.rs` → plain OpenTelemetry
  (`opentelemetry` + `opentelemetry_sdk` + `opentelemetry-http`, pinned
  exactly as a family).
- `datadog/` builds `src/bin/relay-datadog.rs` → Datadog's official Rust SDK
  (`datadog-opentelemetry`, from
  [dd-trace-rs](https://github.com/DataDog/dd-trace-rs)) with the
  `opentelemetry` and `opentelemetry-http` requirements set to what that
  release of the SDK declares.
- `none/` builds `src/bin/relay-none.rs` → nothing installed; the API
  crates are ordinary application dependencies.

The split exists because the tracers are versioned independently and the
OpenTelemetry API crate must resolve to **one copy** per binary:
`datadog-opentelemetry` requires an exact `opentelemetry` (0.6.0 → `=0.33.0`),
and with two copies in a lock the SDK installs its propagator in one while
the relay's `global::get_text_map_propagator()` reads the other — the build,
boot and delivery checks all pass and nothing is injected (the 2026-11-01
back-tests of 0.3.2–0.4.0 show 0/16 for exactly that reason). In one shared
crate that forced `otel-rust` to sit at whatever `opentelemetry` the Datadog
SDK required; with a crate per tool the otel pin moves freely and the
datadog crate's API requirement follows its SDK (`pins.yaml`: `follow`).
`cpm pins check` still refuses a second copy of a pinned or followed crate.

Build: `relays/rust/Dockerfile` with build context = repo root (for
`proto/relay.proto`) and `--build-arg TOOL=otel|datadog|none`, matching
relays/go/Dockerfile; it copies `src/`, `build.rs` and the selected tool's
manifest and lockfile only.

## Transport libraries

| leg | library |
|---|---|
| HTTP server | axum 0.8 |
| HTTP client | reqwest 0.13 (no TLS backend — the sink is plain http) |
| gRPC server / client | tonic 0.14 (stubs generated by tonic-prost-build from `proto/relay.proto` in build.rs) |
| Kafka | rust-rdkafka 0.39 (`StreamConsumer` / `FutureProducer`, librdkafka built via the `cmake-build` feature) |
| RabbitMQ | lapin 4 (tokio runtime, no TLS backend) |

## Carriers (all documented propagator API usage)

Implementing `opentelemetry::propagation::{Injector, Extractor}` over a
library's native header container is the documented way to drive the OTel
propagator where no pre-built carrier exists; the propagator alone decides
header names/values.

| transport | carrier | documented source of the pattern |
|---|---|---|
| HTTP (axum in, reqwest out) | `opentelemetry_http::{HeaderExtractor, HeaderInjector}` over `http::HeaderMap` — used directly, no custom impl | the official [opentelemetry-http](https://docs.rs/opentelemetry-http) carrier crate; also the exact types Datadog's Rust docs use in their inject/extract examples |
| gRPC (tonic) | `MetadataExtractor` / `MetadataInjector` over `tonic::metadata::MetadataMap` | opentelemetry-rust's [tracing-grpc example](https://github.com/open-telemetry/opentelemetry-rust/tree/main/examples/tracing-grpc) (`MetadataMap` carrier) |
| Kafka (rdkafka) | `KafkaHeaderExtractor` over `BorrowedHeaders`, `KafkaHeaderInjector` over `OwnedHeaders` (record headers) | Extractor/Injector traits implemented over rdkafka's own [record-header types](https://docs.rs/rdkafka/latest/rdkafka/message/struct.OwnedHeaders.html); `OwnedHeaders::insert` is consuming, hence a swap in `set` |
| RabbitMQ (lapin) | `AmqpHeaderExtractor` / `AmqpHeaderInjector` over `lapin::types::FieldTable` (`basic.properties` headers; values as AMQP long-strings) | same trait-over-native-container pattern; `FieldTable` is lapin's [documented header table type](https://docs.rs/lapin/latest/lapin/types/index.html) |

We considered `axum-tracing-opentelemetry`/`tower-otel`-style middleware for
the HTTP legs but chose the official `opentelemetry-http` carriers instead:
they come from the opentelemetry-rust project itself, they are what Datadog's
Rust docs demonstrate, and they keep both variants on identical code paths
(third-party tower middleware bridges through the `tracing` crate and pins
its own SDK versions).

## otel (`relay-otel`)

- Global propagator set explicitly to composite
  `TraceContextPropagator` + `BaggagePropagator`. **The Rust SDK does not
  read `OTEL_PROPAGATORS`** (env-based propagator configuration is not
  implemented in opentelemetry_sdk 0.32), so the compose-level
  `OTEL_PROPAGATORS=tracecontext,baggage` is echoed in `/info.config` but the
  actual configuration is the hardcoded equivalent.
- The `SdkTracerProvider` is real but has **no exporter registered**: spans
  are created and sampled (default `ParentBased(AlwaysOn)`), so downstream
  injection carries fresh span ids instead of pass-through — same rationale
  as relays/go/otel. `OTEL_TRACES_EXPORTER` is likewise not read by the Rust
  SDK; not registering an exporter is the equivalent.
- Because there is no instrumentation middleware, the relay itself starts one
  server/consumer span per inbound message and one client/producer span per
  outbound call via the documented `Tracer`/`span_builder` API — this is the
  minimal span structure real instrumentation would create, and it is what
  makes the injected span id differ from the seeded one.

## datadog (`relay-datadog`)

Datadog's official Rust SDK ([Tracing Rust Applications](https://docs.datadoghq.com/tracing/trace_collection/automatic_instrumentation/dd_libraries/rust/);
the SDK is **in Preview**). `datadog_opentelemetry::tracing().init()` is the
[documented entry point](https://docs.rs/datadog-opentelemetry): it reads
DD_* env configuration and installs both the Datadog `SdkTracerProvider`
**and** the Datadog composite `TextMapPropagator` globally, after which the
relay's shared OTel-API code (carriers, spans, `global::get_text_map_propagator`)
runs unchanged. With no Datadog agent container, export attempts fail and
traces are buffered/dropped; header injection is unaffected (see DESIGN.md).

Propagation styles (verified against the crate's
[`TracePropagationStyle`](https://docs.rs/datadog-opentelemetry/latest/datadog_opentelemetry/configuration/enum.TracePropagationStyle.html)
docs and the 0.5.2 source):

- `DD_TRACE_PROPAGATION_STYLE` **is honored**, comma-separated, for both
  extract and inject (with `_EXTRACT`/`_INJECT` overrides). `OTEL_PROPAGATORS`
  is accepted as a lower-precedence fallback alias.
- Supported styles: `datadog` (`x-datadog-trace-id`/`x-datadog-parent-id`/
  `x-datadog-sampling-priority`/`x-datadog-tags`), `tracecontext`
  (`traceparent` + `tracestate`; foreign tracestate entries are parsed and
  re-emitted, with Datadog's own `dd=` entry added), `baggage` (W3C — the
  crate delegates to the OTel SDK `BaggagePropagator`), `b3multi`,
  `b3` (single header), `none`.
- Source-verified default (env unset): `datadog,tracecontext,baggage` —
  matching the documented default for Datadog SDKs.
- Docs discrepancy, recorded deliberately: the
  [Trace Context Propagation](https://docs.datadoghq.com/tracing/trace_collection/trace_context_propagation/?tab=rust)
  page's Rust tab lists only `datadog` and `tracecontext` and footnotes
  "`baggage` is not supported in Rust", but datadog-opentelemetry 0.5.2
  implements baggage extract/inject (`src/propagation/baggage.rs`) and
  defaults it on. The matrix run measures what actually happens, so the
  empirical result stands either way.
- `ot-baggage-*` (OpenTracing legacy): no support in the Rust SDK — there is
  no OpenTracing style in the enum, so these headers are expected to drop.

## Shared notes / caveats

- **Explicit context plumbing.** Rust has no ambient request context;
  `Context::attach()` guards don't survive `.await` without extra machinery,
  so the relay passes `opentelemetry::Context` values explicitly from the
  inbound handler to the outbound call — the same exception DESIGN.md grants
  Go, for the same reason. The outbound call still happens inside the inbound
  handler/consumer callback, so "current context" semantics are honest.
- **Consumers never crash the process.** The rdkafka consumer retries client
  creation and logs+continues on `recv` errors (librdkafka reconnects
  internally); the lapin consumer reconnects with a 2s backoff on any
  connection/consume failure. The RabbitMQ publish side keeps a
  lazily-connected channel and drops it on failure so the next test
  reconnects; the tonic channel is `connect_lazy`.
- Queue/topic contract: consume `RELAY_TOPIC` (default `relay-in-{VARIANT}`),
  group `relay-{VARIANT}`, `auto.offset.reset=earliest`; consume
  `RELAY_RABBIT_QUEUE` (default `relay-rmq-{VARIANT}`) declaring
  durable=false/auto_delete=false/exclusive=false; both the relay and sink
  queues are declared defensively (idempotent), matching relays/node.
  RabbitMQ deliveries are acked even on handler error (never redeliver-loop
  in the harness, matching relays/node).
- `/info` versions are stamped at build time by `build.rs` from the tool's
  `Cargo.lock` (`tracer_version` = the `opentelemetry` or
  `datadog-opentelemetry` crate version; `libs.propagation` lists the
  OpenTelemetry crates that lock holds) and `rustc --version`; no runtime
  lookups. Docker builds use `--locked` so the stamped versions always match
  the committed lockfile.
- Dockerfile uses `rust:1.9x-bookworm` (not 1.8x): the 2026 dependency tree's
  MSRVs have moved past 1.8x, and it matches the toolchain the committed
  lockfiles were generated with. `cmake` is installed for rdkafka's
  `cmake-build` (vendored librdkafka, zlib statically linked via
  `libz-static`) and `protobuf-compiler` for tonic-prost-build. The COPY
  paths are explicit because the repo root has no `.dockerignore` — a blanket
  `COPY relays/rust` would drag a local `target/` into the image build.
- tonic 0.14 split protobuf codegen out of `tonic-build`: the build script
  uses `tonic-prost-build`, and the generated code needs the `tonic-prost`
  runtime crate.
